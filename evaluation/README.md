# Evaluation baseline

corpus.json contains 300 **synthetic** examples: 200 benign and 100 phishing. Fifteen manually specified scenario families each have twenty deterministic variants. The labels describe intended behavior; they are not generated from classifier output. Some synthetic suffixes are intentionally non-resolving. Every resource is fulfilled locally during evaluation.

The tuning split has 100 benign and 60 phishing examples. The evaluation split has 100 benign and 40 phishing examples. Family IDs and registrable domains cannot overlap the splits; both the evaluation runner and a unit test enforce that rule. Variants within a family remain correlated. This is a regression corpus, not an independently collected or representative security benchmark.

Run npm run evaluate to rebuild the evaluation bundle, execute shared detection and submission policy in Chromium, and replace latest-report.json. The report includes the corpus SHA-256, browser version, individual results, false warnings, precision, recall, benign/phishing interruption rates, and scan latency. Latency is wall time including idle scheduling; it is not a measure of main-thread blocking.

The historical rules-version-2 baseline warned on 100/100 synthetic phishing examples and 20/200 benign examples, using index >=30 as the warning definition. All twenty false warnings came from cross-site HTTPS SSO forms. No benign submission was interrupted; 60/100 phishing submissions were interrupted.

Rules version 3 measures actual evidence-policy alerts, excluding passive destination/link notices. On the same unchanged 300 fixtures: 100/100 phishing alerts, 0/200 benign alerts, 20 passive SSO destination notices, no benign interruptions, and 80/100 phishing interruptions. All 300 diagnostic scores are unchanged from the committed version-2 baseline. The twenty additional interruptions are credential forms on brand-subdomain impersonation fixtures, which no longer need extra URL keywords to cross an index cutoff. This is a deliberate policy and presentation change, not evidence of calibrated risk or improved real-world classification. The old report remains available in Git history before this revision.

Independent real-world page sets and legitimate login integrations are needed before a broader release. Results from this small correlated synthetic set must not be advertised as production accuracy. See [the evidence policy and sources](SCORING.md).

The [manual test matrix](MANUAL-TESTS.md) separates credential protection from AMTSO signature checks and browser connection-security tests. `npm run evaluate:branding` writes `form-branding-report.json`, comparing the original 300 cases and 24 targeted cases with the same scanner/guard and explicit baseline/candidate switches. Targeted labels include benign, phishing and a separate intentional insecure-transport case. The latter is not counted as a benign-login interruption. Under version 3's alert definition, the candidate adds six targeted phishing alerts and two benign alerts (enterprise-login and SSO), with zero benign interruptions; promotion fails and form-context branding remains disabled. Version 3 comes from the separate evidence-policy change, not candidate promotion. Paired timings alternate execution order and do not establish production latency. The corpus and source fingerprints identify the measured inputs.

For offline AI comparison, run node scripts/export-ai-evaluation.mjs. This exports only synthetic held-out hostname/rule IDs and bounded semantic text, never user pages. There are no model calls. Collect reviewed model responses separately as a JSON object mapping IDs to {\"escalate\":true|false,\"reason\":\"at most 300 characters\"}, then run npm run evaluate -- --ai-results FILE. The runner reports the counterfactual warning metrics; live AI remains advisory-only regardless of results. No model has been evaluated or approved for automatic escalation.
